(`../Game_of_Life_A/docs/INTERFACE.md`), extended with the scope Anthony
required: **1D and 2D domain decomposition** and **six halo backends**

`include/life.h` and `src/life.c`; this project only adds the parallel drivers
and the halo transport. One implementation of the mathematical semantics
therefore serves serial, MPI and hybrid runs.

## Command line

```bash
mpirun -np 4 ./build/mpi --rows 1024 --cols 1024 --steps 500 \
    --seed 42 --density-ppm 500000 --output final.pbm

OMP_NUM_THREADS=4 mpirun -np 2 ./build/hybrid --rows 2048 --cols 2048 \
    --steps 500 --seed 42 --density-ppm 500000

mpirun -np 8 ./build/mpi --input initial.pbm --steps 100 --output final.pbm
```

`--rows`, `--cols`, `--steps`, `--seed`, `--density-ppm` mirror A's serial CLI.
`--input` and `--output` use P1 PBM. `--seed`/`--density-ppm` are rejected
together with `--input`. `--decomp 1d|2d` picks the domain decomposition
(default `1d`, the validated baseline);
`--comm blocking|nonblocking|overlap|rma|persistent|sendrecv2` picks the
halo-exchange backend (default `blocking`). Both are optional and
default to the historical behaviour. Rank 0 writes one JSON object to stdout
with two additive fields `decomp` and `comm`; diagnostics go to stderr.

## Parallel design

Full design, message tags and synchronization semantics:
[INTERFACE.md](INTERFACE.md). Summary:

- **Decomposition `--decomp 1d`.** Contiguous row blocks: `local_rows(p) = H/P +
  (p < H%P)`, `global_offset(p) = p*(H/P) + min(p, H%P)`. Requires `1 <= P <= H`.
- **Local storage.** A's `LifeGrid` with `rows = local_rows`,
  `cols = global W` and `stride = W+2`. Owned cells are `r=1..local_rows`,
  `c=1..W`; row 0 and row `local_rows+1` are the vertical ghosts.
- **Horizontal ghosts.** `life_wrap_horizontal` fills `c=0` and `c=W+1` for
  every owned row before each exchange.
- **Vertical halo.** Two `MPI_Sendrecv` calls exchange complete `stride`-byte
  rows, so corner cells travel with the halo:
  first owned row to the previous rank / receive the next rank's first row into
  the bottom ghost (tag `TAG_UP`); last owned row to the next rank / receive the
  previous rank's last row into the top ghost (tag `TAG_DOWN`). Each call pairs
  its send with a receive from the opposite neighbour, forming a ring within the
  call. Pairing both directions of one call with the same neighbour deadlocks
  for every `P >= 2`.
- **P = 1 / P = 2.** With one rank the ghosts are copied with `memcpy`; with two
  ranks the upper and lower neighbour coincide, which is safe because the two
  tags differ and the send/receive buffers never overlap.
- **Update.** `life_update_row` reads the previous buffer and writes the next
  buffer; grids are swapped after the loop. `-DGOL_USE_OPENMP` parallelises the
  row loop with `schedule(static)`; all MPI calls stay outside parallel regions.
- **Collectives.** Rank 0 packs the interior of the full grid into a contiguous
  buffer, `MPI_Scatterv` distributes it, and `MPI_Gatherv` returns the owned rows
  in global order. Rank 0 then unpacks, computes diagnostics, and writes the PBM.
- **MPI threading.** `MPI_Init_thread(..., MPI_THREAD_FUNNELED, ...)`; the
  program refuses to run if that level is not provided.
- **Decomposition `--decomp 2d`.** Periodic Cartesian process grid
  (`MPI_Cart_create`, `reorder=0`; most balanced factor pair with
  `a <= H`, `b <= W`, chosen rank-locally). Each rank owns a self-contained
  `LifeGrid` with ghost rings on all four sides; edge and corner ghosts travel
  as eight tagged segments (tags named after the receiving ghost segment, so
  neighbour-role aliasing in 2x2 grids stays unambiguous). Scatterv/Gatherv
  use a block-major layout because 2d row blocks are not contiguous globally.
- **Halo backends `--comm`.** `blocking` = Sendrecv ring pairs (unchanged
  baseline); `nonblocking` = Irecv-before-Isend plus Waitall;
  `overlap` = nonblocking posts, interior rows computed between post and
  Waitall, border rows after; `rma` = `MPI_Win_create` + `MPI_Put` with one
  fence pair per step (complete/access epochs; ghost columns staged through a
  contiguous auxiliary window); `persistent` = `MPI_Send_init`/`MPI_Recv_init`
  registered once per grid buffer (`Startall`/`Waitall` each step, active set
  follows the `step & 1` parity like the RMA windows);
  `sendrecv2` = explicit `MPI_Send`/`MPI_Recv` ring shifts, staggered by rank
  parity (even ranks send first) so the wait graph is acyclic. All six fill
  identical ghost bytes, so the final grid is backend-independent.

## GPU variant (OpenMP target offload)

`make gpu` adds `-DGOL_USE_OMP_TARGET`; the binary reports `"variant":"gpu"` and
`"threads":1`. Design, in one line: the grid never leaves the device during the
run, so per step only four rows cross PCIe — the two rows MPI sends, and the two
ghost rows MPI receives.

- Both `LifeGrid` buffers are mapped once (`target enter data map(to:...)`) and
  released once at the end, so the kernel touches device memory directly.
- The kernel folds the periodic column wrap in
  (`cl = c==1 ? cols : c-1`, `cr = c==cols ? 1 : c+1`), which is the same rule
  `life_wrap_horizontal` implements. The host copy of the grid is therefore
  intentionally stale between steps and the host wrap is skipped.
- `gpu_fetch_edges` pulls owned rows 1 and `local_rows` back before any MPI
  call (they are the halo send sources); `gpu_flush_ghosts` pushes the two
  received ghost rows to the device before the next kernel. Both sit inside the
  existing `halo_post`/`halo_finish` pair, so all four comm backends and the
  overlap schedule keep working unchanged.
- `--decomp 2d` is rejected by the GPU build: the 2D halo needs every row's
  first and last column on the host, which contradicts the "only ghost rows
  travel" design. Failing loudly beats silently wrong results.
- With no device visible the binary refuses to run rather than falling back to
  the host. `GOL_ALLOW_HOST_TARGET=1` overrides that for logic-only checks
  (checksum/wrap/halo testing on a CPU-only machine); such a run is **not** a
  GPU measurement and must not be reported as one.

Status: measured on Vanda (A40, job 1524542, `batch_gpu`, 36 cores + 1 GPU).
The device checksum matrix is **PASS=32, FAIL=0** (5 grids x ranks 1/4 x 4 comm
backends). Same-node, same-NVHPC comparison, 300 steps, best of 3:

| grid | GPU | 36 CPU threads | GPU relative |
|---|---|---|---|
| 2048² | 0.2505 s | 0.1245 s | 2.01x slower |
| 4096² | 0.4919 s | 0.4653 s | 1.06x slower |

The GPU loses because every step still hands four rows across PCIe and launches
one kernel (the 1D halo is host MPI); that fixed cost amortises with grid size,
while the kernel is bound by uint8 memory traffic rather than float throughput.
Beating the CPU needs the halo to stay on the device (CUDA-aware MPI / NVSHMEM),
which is out of scope. Two NVHPC-specific facts found while getting there: a
target region may not hold only a declare-target call (NVC++-S-0155), so the
loop is inlined; and the blocking backend finishes inside `halo_post`, so the
ghost push must happen there too — before that fix, only the blocking cases
failed. Both GPU batch submissions (free pool and `batch_gpu`) ran the
checksum matrix before recording timings; the PBS wrappers themselves are
excluded from this repository.

## Timing contract

- `kernel_seconds`: all iterations, including horizontal wrap, halo exchange,
  update, synchronisation and swapping. Excludes initialisation, gathering,
  diagnostics and file output.
- `total_seconds`: allocation, input/initialisation, iterations, final gather
  and diagnostics. Excludes PBM and JSON writing.
- Both are reduced with `MPI_MAX` over ranks after a synchronised start.
  `seconds = kernel_seconds` is the only value used for speedup.
- Optional instrumentation (off by default, never mixed into CSV timing):
  `GOL_HALO_STATS=1` adds a `halo_seconds` JSON field — wall time inside
  `halo_post`/`halo_finish` only (interior compute excluded), max-reduced like
  the other timers. `GOL_TRACE=1` prints per-rank stage markers on stderr to
  locate wedged collectives in remote batches.

`make test` installs both binaries into A's `build/`, builds A's serial

The reported test suite is A's 90-test validation suite
(`../Game_of_Life_A/docs/VALIDATION_SUITE.md`); the 773 figure is the
underlying execution count, not 773 hand-written tests. Where they come from —
14 + 512 + 84 serial cases, plus 163 external runs, each case counted once per
configuration:

| Group | Count | What it is |
|---|---|---|
| Named cases | 14 | Known-answer tests, checked without the oracle: empty, single dies, block (stable), blinker odd/even, corner block, edge blinker, glider 4 steps, glider wrapping the border, 1x1, all alive, zero steps, local row of 1, non-divisible rows |
| Exhaustive 3x3 | 512 | Every `2^9` initial state of a 3x3 grid, one step. This exhausts the rule's input space, so the update rule is proved rather than sampled; each case is 9 cells and finishes in milliseconds |
| Random shapes | 84 | 14 shapes (`1x1` up to `31x37`, including single row/column) x 6 density/step pairs (`p=0.05..0.95`, steps `0,1,2,3,10,25`) |
| External variants | 163 | The 14 named cases replayed on the real parallel binaries: `mpi` at ranks 1/2/4/8 (43 runs, ranks > rows skipped) and `hybrid` at ranks 1/2/4 x threads 1/2/4 (120 runs) |

The count is execution count, not 773 hand-written tests. The 512 exhaustive
cases are the largest block and also the strongest one; the matrix is small in
wall-clock terms but broad in coverage.

`scripts/test_comm.sh` additionally covers the new `--decomp`/`--comm` paths:
for each grid it takes A's serial checksum as ground truth, then runs
`DECOMPS x COMMS x RANKS` (default grids `64x64 97x53 5x13`, ranks `1 2 3 4 8`,
which exercises uneven blocks, non-square process grids, and — via 5x13 at
np=8 — single-column blocks in a 2x4 process grid, the extreme behind A's
validation-suite cases D20/D21), checks the JSON required fields plus the
`decomp/comm` echo, and repeats one `--input` run per backend at 4 ranks.

Atlas result with `foss/2025b` (GCC 14.3, OpenMPI 5): interface 1.0 regression
**PASS=773, FAIL=0, BLOCKED=0** and the `decomp x comm x ranks` matrix

`results/vanda_correctness/test_comm.log` shows PASS=88/FAIL=0 for the

```bash

```

Defaults: seed 20261026, density 500000, 500 steps, repeat 3, grids 1024 and
2048, ranks 1/2/4/8, hybrid pairs `1x8 2x4 4x2` (a fixed 8-core budget, matching
A's `config/experiment_plan.csv`). `HYBRID_PAIRS` entries are `ranks x threads`.
`DECOMPS` (default `1d`) and `COMMS` (default `blocking`) loop the MPI runs
over the new options; hybrid runs stay on the `1d/blocking` baseline.

Knobs: `GRIDS` accepts `WxH` for non-square grids (weak scaling);
`SKIP_SERIAL=1` drops the serial baseline (large grids); `APPEND=1` keeps an
existing CSV instead of rewriting the header (one call per weak-scaling level);
`HYBRID_PAIRS=""` disables hybrid runs (Vanda builds only `build/mpi`);
`RUN_TIMEOUT=900` caps each run so a wedged launcher fails loudly instead of
stalling the batch.

CSV fields: `mode,W,H,steps,ranks,threads,repeat,kernel_seconds,
total_seconds,live_cells,checksum,job_id,decomp,comm`. The last two columns
are new; readers that ignore trailing columns stay compatible, and
`summary.py` falls back to `1d/blocking` for old CSVs. The hybrid runs set
`OMP_NUM_THREADS`, which is also the `threads` value reported in the JSON.

### Queue routing (measured 2026-11-04 with `qstat -Qf`)

| Queue | Routing / limits | Cost | Can host 256 cores? |
|---|---|---|---|
| `auto_free` | routes to `cpu_serial` (max 1 ncpu), `cpu_parallel` (max 160 ncpus, nodect 10), `gpu` (max 36 ncpus, min 1 GPU) | free (`queue_charge_rate=0`) | **no** — 256 > 160 |
| `auto` (default) | routes to `batch_cpu`, `batch_gpu` | charged | yes |
| `batch_cpu` | max 720 ncpus, nodect 10, `max_run_res.ncpus=720`, `from_route_only=True` | `queue_charge_rate=1`, billed to `project` | **yes** — 4 x 64 fits |

Consequences, all checked rather than assumed:

- A 256-core job must go to `auto` (which routes into `batch_cpu`); submitting
  it with `-q auto_free` leaves it queued forever. The 256-rank batches used
  `-q auto`, the free batches `-q auto_free`.
- No `#PBS -P` is needed: a probe job (1518788, `/bin/hostname`, 1 core) landed
  on `batch_cpu` and exited 0. The charge is therefore real and lands on the
  submitting account's own project.
- A held 256-core probe (`qsub -h -q auto -l select=4:ncpus=64:mpiprocs=64`,
  job 1518784) was accepted by the server and then deleted, so the resource
  request itself is legal.
- Cost is now bounded by walltime, not by the stage composition: the paid job
  is capped at 12 minutes, so the worst case is 4 x 64 x 12 min = 51.2
  core-hours. Expected wall is well under that (stage 0 is ~1 min, the three
  measured points follow). Everything serial and everything up to 128 ranks
  moved into the free job, so no core-hours are spent on baselines.

### Launch mechanics

- Free-queue batch (local wrapper): `select=2:ncpus=64:mpiprocs=64` = 128 ranks,
  `-q auto_free`. Strong scaling 4096² at 1/4/16/64/128, weak scaling 1024²
  cells per rank at 1/4/16/64, backend comparison at 64/128 ranks. Hybrid
  disabled; serial baseline rebuilt with the Vanda toolchain.
- 256-rank batch (local wrapper): `select=4:ncpus=64:mpiprocs=64` = 256 ranks,
  `-q auto`, `walltime=00:12:00`. Stage 0 is a 256-rank preflight at 512²
  (20 steps, all eight `decomp x comm`, REPEAT=1) with `set -e`, so a broken
  launch aborts in about a minute. Stages 1-3 reuse the free job's sweep
  definitions restricted to 1/64/256.
- SSH wrapper (local, not in this repo): OpenMPI `plm_rsh` re-execs `ssh` from `PATH` to start
  `orted` on peer nodes; the job copies it to `bin/ssh` and prepends `PATH`
  (BatchMode, no host-key prompts, 15 s timeout). Compute nodes get no module
  environment over ssh, hence `mpirun --prefix <mpi-root>`.
- `--bind-to none` is required: hwloc under Vanda's PBS cpuset misreports
  socket/core capacity — socket binding aborts, core binding can wedge.
  Slots equal ncpus, so ranks stay on allocated cores regardless.
- Node shape (measured): `pbsnodes` reports `cn-001` with `pcpus = 72` and
  `resources_available.ncpus = 72`, so 4 x 64 = 256 across 4 nodes is
  satisfiable. (An earlier note claiming 36 cores per node was wrong.)
- Job history (measured): all 19 jobs this account has run on Vanda were
  `select=2:ncpus=16` or `select=2:ncpus=32` — 16 or 32 ranks, never more.
